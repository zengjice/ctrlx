# CtrlX Personal Agent 产品调研与设计草案

初稿：2026-10-04。更新与竞品资料核对：2026-10-12。状态：产品探索，尚未确定开发排期。

CtrlX 的首个产品假设是：让已有 AI 用户从手机直接检查、修改和继续自己电脑上的实际工作，以一次完整的远程验收形成安装理由，再通过重复使用成为项目的日常入口。

保留三个候选方向：实时界面与远程接管、从用户演示中形成可复用工作流、跨用户的 Agent 协作。其中，模拟器、浏览器、文件浏览器是实时界面方向下的三类工作对象，不另外算三个产品方向。首轮优先验证实时界面；演示学习先收窄到问题复现与重复验收，跨用户协作先做小范围实验。

本地执行、远程访问、Agent 对话和演示学习都已有竞品覆盖，不能直接作为独有优势。下文区分官方资料确认的能力、CtrlX 当前实现与待验证的产品假设；AgentHop 的源码实验仍限定在 2026-10-04 检查的版本。

## 产品定位

CtrlX 可以承载一种在用户自己的 Mac 上执行、由用户从 Mac 或手机访问的 Personal Agent。它复用用户已有的 Agent、项目、文件和本地工具，让用户在任务运行期间能介入决策，并检查真实结果。候选对外表达是：**用手机，直接检查和修改 AI 在你电脑上做出的成果。**

先争取一类任务的使用，让用户继续保留熟悉的 ChatGPT、Claude 等客户端。第一次安装可以由一次离开电脑后的修改需求触发；持续使用则取决于项目文件、运行界面、反馈和结果能否在同一个入口里衔接。普通聊天历史和提示词库的整体迁移不应成为首次使用前提。

本地执行、远程控制、多 Agent 接入是这套产品的基础。三个候选方向分别回答三个更具体的问题：我能否直接看到并操作结果；它能否复用我做事的方法；它能否与别人的 Agent 一起完成工作。

“本地执行”指工具和任务的执行位置。模型推理仍可能调用云端服务，发送给模型的数据遵循对应服务的边界。远程执行也依赖 Host Mac 在线且可运行任务；电脑休眠、关机或 Agent 进程退出后的行为需要明确呈现。

## 竞争情况与差异化边界

以下为截至 2026-10-12 的官方文档能力核对，功能可用性受套餐、平台、组织设置和逐步开放影响。这些资料可以证明功能重叠，不能替代同一真实任务下的易用性、可靠性和耗时比较。

| 产品与能力 | 官方资料确认的范围 | 对 CtrlX 的影响 |
| --- | --- | --- |
| OpenClaw 本地助手 | 在自己的设备运行，通过已有通信渠道访问；模型和 Agent 执行程序可通过插件替换。[README](https://github.com/openclaw/openclaw/blob/main/README.md) | 本地运行、沿用聊天入口和多 Agent 接入已有先例 |
| Grok Bot 移动端 | 手机可查看云端电脑、接管输入并交回控制；同账号的 Bots 使用同一台云端电脑。[移动端](https://docs.x.ai/grok-bot/mobile) | 实时画面与人工接管本身不独有；需比较面向本机项目的完整体验 |
| Grok Bot 协作 | 群组支持多个 Bot；Bot 可异步发送任务，接收方被唤醒并稍后回复。[消息与协作](https://docs.x.ai/grok-bot/chat-and-collaboration) | Agent 对话不构成独有卖点；跨用户、跨执行程序的任务交接需单独验证 |
| Grok Bot 演示学习与本机访问 | Teach a task 可从演示生成 Skill 草案，逐步开放；本机命令执行有独立设置。[Skills](https://docs.x.ai/grok-bot/skills-routines-and-automations)、[本机访问](https://docs.x.ai/grok-bot/approvals-security-and-privacy) | 不能把演示学习或本机访问描述为竞品空白；云端电脑与本机执行应分开比较 |
| ChatGPT 移动端任务 | 可从手机发起、指导和审批连接电脑上的 Codex 任务，并查看文件改动、差异和测试结果。[移动端](https://learn.chatgpt.com/docs/mobile) | 远程发消息、看状态和审批已经有官方入口 |
| ChatGPT 浏览器与本地工作 | 内置浏览器提供本地网页预览与视觉反馈；Work 可通过桌面端使用获准的本地文件、应用和浏览器。[浏览器](https://learn.chatgpt.com/docs/browser)、[本地执行](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-local-security) | 网页预览、标注和本地文件访问均有重叠，应比较手机上连续修改的步骤与成本 |
| Claude 跨设备工作 | 可跨桌面、网页和手机继续任务；满足会话条件且桌面端在线时，可使用连接的本地文件、浏览器和应用。[跨设备说明](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile) | 本地资源与移动端任务不能作为排他的能力优势 |
| Claude Computer Use | 可操作桌面应用，官方用例包含打开手机模拟器并检查 App 的交互问题。[Computer Use](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork) | 模拟器用例已有覆盖；专门适配的手机操作、反馈与验收流程仍需实测比较 |

Claude 官方说明，自 2026-10-06 起 Pro、Max 的新 Cowork 任务转为云端运行，本地资源仍通过桌面端访问；需要本机执行的用户也可使用 Claude Code。这个变化体现了云端持续运行与本机环境访问的组合，不能推导为 Claude 不再支持本地工作。[执行位置说明](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)

CtrlX 的可验证差异应集中在：更少的人工上下文转述、更顺畅的手机接管与验收、不同 Agent 使用同一套项目资源和结果入口。跨 Agent 复用应传递明确的项目资料、产物和交接摘要，不承诺无损继承另一家客户端的对话、记忆或订阅权益。

功能被官方客户端补齐的风险很高。长期价值需要来自针对具体工作的操作质量、可靠性和用户已经验证过的方法。多模型入口、加密或本地部署可以服务特定偏好，但单独存在不足以证明普通用户愿意安装和付费。

## Personal Agent 热度的产品启示

OpenClaw 将设备上的助手、已有通信入口和可扩展工具组合在一起。[项目说明](https://github.com/openclaw/openclaw/blob/main/README.md) 以下是对这类产品再次获得关注的机制假设，不是对某次增长的已验证因果归因：

- 当模型和工具的组合能更可靠地交付结果，同样的产品概念可能跨过用户愿意日常使用的门槛；需要用任务成功率验证。
- 沿用熟悉入口、减少配置与材料搬运，可能提高从看到演示到首次成功的转化；需要观察完整安装与首次任务流程。
- 可见的操作、完成的产物和可复用的方法容易被演示与分享，可能促进传播；观看、安装和付费留存需要分别衡量。

对 CtrlX 的启示是用一段可复现的真实任务演示获客，再用之后的自主重复使用判断需求。公开关注度和演示传播不足以判断用户会持续承担安装、主机在线和额外付费的成本。

## 目标用户与安装路径

| 用户 | 可能触发安装的需求 | 首轮取舍 |
| --- | --- | --- |
| 已在 Mac 上使用 Claude Code、Codex 等 Agent 的开发者 | 离开电脑后检查 App 或网页、处理阻塞并继续原任务 | 最贴近当前基础；优先选择经常有远程验收需求的人 |
| 用 AI 制作网页、小应用和自动化的独立创作者 | 直接查看成果、挑选本地素材、指出问题并继续修改 | 与开发者相邻的扩展人群；需要简化执行环境与登录配置 |
| 经常处理本地文档和素材的办公用户 | 手机取用材料、预览产物并指定文件继续处理 | 用文件任务做后续验证，先限定文件类型与操作范围 |
| 主要进行问答、写作和陪伴聊天的用户 | 当前缺少足够强的额外安装理由 | 不作为首轮获客对象 |

首先邀请已有远程需求的用户接入一个真实项目。手机配对后直接打开该项目的可操作结果，完成一次“发现问题—反馈—修改—验收”。初次体验不要求建立联系人网络、配置多 Agent 团队或整理完整知识库。

ChatGPT、Claude 聊天客户端用户与本地 CLI 用户的迁移成本不同。CtrlX 当前复用 tmux 中的 Agent 会话，不能直接视为已经接管官方桌面客户端的聊天。面向聊天客户端用户，需要单独验证执行引擎接入、账号授权、项目资料导入和费用说明。

截至本次检查，README 仍注明 Mac 分发包未公证，iOS 需要本地签名构建。这会显著增加非开发者试用的门槛。面向普通用户的安装与分发体验应作为获客验证的前置条件；技术用户愿意自行签名，不能证明大众用户也愿意。[安装说明](../README.md)

付费假设是用户愿意为减少回到电脑、搬运材料和重复解释支付额外费用。访谈和试用应把 CtrlX 费用、模型费用、配置与维护时间一起算入，不以用户已有模型订阅自动覆盖新执行环境为前提。

## 三个候选方向

| 方向 | 用户可以直接理解的体验 | 安装与持续使用的动机 | 当前基础与缺口 |
| --- | --- | --- | --- |
| 实时界面与远程接管 | 在手机上操作本机的网页、App 和项目文件，指出问题，再交给 Agent 继续 | 离开电脑也能检查结果和推进任务 | 已有远程终端和 Agent 状态；三类工作对象的远程操作与任务关联需要扩展 |
| 演示学习与工作流复用 | 用户示范一次操作方法，Agent 整理成可检查、可重复执行的工作流；先验证问题复现与验收步骤 | 常做的事情逐渐少教、少做，个人方法可以积累 | 浏览器和模拟器提供部分观察与操作基础；演示采集、归纳、验证和复用尚待设计 |
| 跨用户的 Agent 协作 | 邀请同事的 Agent 处理共同任务，双方在各自环境工作，用户能查看进展并确认结果 | 减少人工转述和环境交接，完成单方难以独立完成的工作 | 已有多 Agent 状态接入和设备远程访问；跨用户身份、任务邀请、授权和会话路由需要新增 |

这三个方向可以共用任务记录和交互入口，但应分别验证需求。实时界面服务于当前任务，演示学习沉淀可复用的方法，跨用户协作连接不同用户的任务和环境。

## 实时界面与远程接管

### 核心场景

用户让本机 Agent 修改网页或 iOS App，随后离开电脑。Agent 完成修改并运行结果后，用户在手机上打开对应任务，直接查看实际运行界面，点击、滚动或输入，指出具体问题，再让 Agent 继续修改。

实时界面同时承担过程观察和结果验收。默认让任务在后台推进，完成或需要决策时通知用户，一键进入对应成果。持续盯着 Agent 的操作不是必要流程，也不把观看时长作为成功指标。

用户应能明确区分实时画面、历史截图和录制回放；正在显示的界面应绑定到正确的 Host、项目、Agent 会话和运行实例。

### 三类工作对象

| 界面 | 核心操作 | 需要减少的人工工作 | 首轮验证重点 |
| --- | --- | --- | --- |
| iOS Simulator | 查看真实 App、点击、滚动、输入、指出问题，再交回 Agent | 回电脑打开模拟器、描述复现步骤、重复确认当前版本 | 手机验收的可操作性，以及反馈是否足以让原 Agent 复现并修正；不替代真机测试 |
| 浏览器 | 打开本机实际运行页面、操作流程、标注问题、接管并恢复 | 截图搬运、解释页面状态、切换应用与窗口 | 与官方客户端及现有远程工具比较，是否更快完成一轮修改 |
| 文件浏览器 | 浏览授权目录、选择输入、预览最新结果，将选中文件交给 Agent 继续处理 | 上传下载中转、复制路径、寻找刚生成的文件、说明改哪一份 | 文件身份、更新时间与任务关联是否清晰；取文件与继续修改能否衔接 |

模拟器适合用具体开发任务展示价值；浏览器连接网页工作；文件操作有机会扩展到办公与创作。它们共享项目与任务入口，但功能投入由实际需求决定，不要求首版同时完成三套完整操作能力。

文件浏览器应采用适合手机的列表、选择和预览，读取 Host 的真实文件状态，不要求把 Finder 窗口作为视频传输。首轮先验证浏览、预览、选择和结果获取，再按场景增加编辑、移动等写操作；通用文件管理器的全部功能不纳入首轮范围。

### 贯穿任务的示例

用户在手机打开“活动页面”任务，看到 Mac 上正在运行的网页；从文件面板选中一张本地图片，说“用这张替换首页封面”。Agent 修改后，用户查看更新后的页面，亲自完成报名流程，指出一个输入问题并让同一会话继续修复。验收通过后，用户可取得最终文件或继续原项目。

iOS 场景使用同样的任务关系：Agent 修改并构建 App，用户进入对应模拟器检查，将当前界面和操作步骤随反馈交回原会话，修复后检查新的运行结果。办公场景则从预览与指定文件继续修改开始，具体格式支持另行确定。

### 建议体验

1. 用户从现有会话创建任务，或把正在运行的工作关联为任务。
2. Agent 打开与该任务关联的网页或模拟器，生成文件关联到同一任务；任务页显示实际结果与当前状态。
3. 用户进入观察模式，看到画面更新时间、连接状态和 Agent 正在做什么。
4. 用户接管输入，Agent 暂停对该界面的写操作；恢复执行由用户明确发起。
5. 用户通过操作、选中文件或界面区域、语音补充要求；反馈携带所指对象及当时状态，交给正确的 Agent。
6. Agent 完成后提供最新运行入口、产物、改动说明和验证结果，由用户检查交付。

用户开始操作时需要有明确的控制权交接，避免人与 Agent 同时修改同一个界面。断线后应显示画面失效状态；重新连接时重新核对运行实例，避免旧输入落到新的页面或设备。

差异化验证集中在三个动作：指得清楚，用户的“这里”和“这份”能附上正确上下文；接得顺畅，人工操作后的状态能交回 Agent；验得明白，通知打开的是本次修改后的结果。普通远程桌面同样能提供画面与输入，CtrlX 需要证明任务关联减少了手动查找、切换和转述。

### 首个验证范围

建议先选择一个受控界面类型，完成“运行、查看、接管、反馈、继续、验收”的完整体验。优先招募有本机项目和远程需求的用户，用模拟器或浏览器中更稳定的一条路径试用，配套最小文件选择与结果获取。界面数量、通用桌面控制和新的 Agent 执行引擎不作为首轮扩张目标。

实时界面是候选方向，不代表 CtrlX 已经支持浏览器或模拟器的远程镜像。Agent Browser 目前限定为本地能力；Mac Viewer 中打开的浏览器仍运行在 Viewer Mac。Agent Simulator 已有本地操作与验收证据，最新输入修复尚待更新签名候选，跨机兼容、公开分发与远程 Viewer 不能由本地证据推定完成。具体实现状态以各自文档为准。[Agent Browser](agent-browser.md)、[Agent Simulator](agent-simulator-design.md)

### 验证方式

让用户用自己的真实任务完成一次远程检查，记录是否仍需要回到电脑、发现问题到发出有效反馈所需时间、人工接管与恢复是否成功，以及画面和输入的端到端延迟。帧率、延迟和并发容量应来自实际端到端测量，分别记录正常网络、断线恢复和多任务负载下的结果。

## 演示学习与工作流复用

### 核心场景

用户有一套经常重复、又难以完整写成提示词的做事方法，例如从业务页面导出指定数据、按固定规则整理，再生成本地报告。用户开启一次教学，亲自操作并解释判断依据，Agent 将这次演示整理成以后可以复用的工作流。

“教一次”是希望降低重复指导成本的产品表达。一次演示只能提供有限样本，工作流需要经过用户检查和不同输入的验证，才能判断适用范围。

### 建议体验

1. 用户在一个明确的任务或受控界面内开始演示，并能看到采集正在进行。
2. 系统记录操作、相关界面状态、输入输出及用户说明；结束教学后停止采集。
3. Agent 生成工作流草案，说明目标、所需输入、步骤、判断条件、输出和需要人工决定的位置。
4. 用户检查并修改草案，确认适用范围和允许执行的动作。
5. 用另一组输入试跑，检查真实产物；遇到歧义或界面变化时暂停并请求补充。
6. 保存经过验证的版本。用户后续可以自然语言调用、修改、停用或导出。

工作流应描述“找到什么、为什么这样做、怎样判断成功”，而不是仅保存坐标和点击序列。能够稳定使用工具、接口或语义化元素定位的步骤优先保留这些表达；确实依赖视觉的操作需要说明环境前提。

工作流可逐步沉淀为可编辑的 Skill、脚本或已有工具的组合。初期优先复用现有机制，具体存储格式在原型验证后确定。一次失败后的修正应保留版本差异，避免悄悄改变用户已经验证过的方法。

### 首个验证范围

建议先在 CtrlX 管理的浏览器或模拟器里，把一次人工发现的问题整理成可复现步骤与验收条件，验证修复后能否再次执行检查。此阶段不承诺自动生成覆盖任意应用的稳定测试，也不要求先建设通用工作流市场。

验证成立后再扩展到文件整理、业务页面操作等高频流程。教学由用户主动开始和结束；采集范围可见。浏览器登录以 CtrlX 自己的 profile 为基础，系统 Chrome 的登录状态不属于当前默认能力。

该方向与实时界面的关系是：用户接管任务时，可以选择把这次操作变成教学材料；接管本身不自动授权记录或学习。

### 验证方式

使用不同输入重复执行同一任务，记录无需修正的成功比例、人工介入次数、结果正确性、节省的操作时间和维护工作流的成本。还需观察用户是否在之后的真实工作中再次调用它。一次演示后的成功回放，只能证明该样本可以重现。

## 跨用户的 Agent 协作

### 核心场景

两名开发者分别掌握前端和后端环境。前端 Agent 发出带任务背景的邀请，后端用户确认后，由后端 Agent 在自己的环境中检查实现、运行测试、回应问题。双方交换必要的接口约定、请求样例、补丁或验证结果，各自保留本地工具和访问权限。

该方向优先验证双方确实拥有不同上下文、账号或运行环境的任务。如果一个 Agent 已经可以访问全部必要资源，就需要评估增加跨用户协调是否仍有收益。

### 建议体验

1. 发起方选择本地项目和 Agent，描述共同目标、期望对方提供的帮助和验收条件。
2. 对方收到任务邀请，选择接手项目与 Agent，确认可共享的信息和允许的动作。
3. 双方 Agent 交换消息和必要产物，各自在本地执行；任务页区分消息送达、正在处理、等待对方、等待用户和待验收。
4. 用户从 Mac 或手机处理需要自己决定的问题，也可以暂停或终止本方任务。
5. 结束时汇总双方达成的约定、实际改动、验证证据与未解决事项；完成状态依据约定的验收条件。

跨用户协作需要独立于现有设备配对的身份和权限范围。联系人可被识别，并不自动获得本机终端控制权或全部项目上下文。邀请、任务执行和向对方共享信息应有明确的授权边界，并留下实际发送内容和产物的记录。

### 首个验证范围

建议从“两名用户、两个独立环境、一次接口联调”开始。初期通过独立进程或 MCP 适配器接入通信能力，保留对方已经使用的 Agent，降低完整安装 CtrlX 的要求。

Host 侧需要统一接收邀请，并路由到正确的项目与 Agent 实例。离线投递、主动唤醒和进程重启后的任务恢复需要各自设计；尚未支持的状态应明确告知用户。现有 CtrlX 的设备配对协议与外部 Agent 通信协议不能直接视为可互换。

### 验证方式

用相同类型的真实任务比较人工转述与 Agent 协作，记录人工转述次数、达到相同结果质量的完成时间、模型与人工介入成本，以及同一对用户是否主动再次使用。邀请带来的传播是待验证假设；双方安装、在线和授权的成本可能抵消收益。

## AgentHop 调研依据

调研日期为 2026-10-04，版本为 v0.6.1，对应提交 0e3e733bc5703856b3924a27c0495c0736a58a92。以下是该版本的事实和本地实验结论，不代表后续版本始终具有相同行为。

### 可借鉴的设计

AgentHop 把创建会话、确认背景、发送消息、报告进度、交换附件和结束会话封装成 CLI 与 MCP 工具。双方使用现有 Agent，各自在自己的环境执行；传输的是显式发出的消息与附件。创建方通过 WebSocket 连接 Relay，加入方通过 HTTP 请求和轮询通信。其 A2A 接口叠加了 AgentHop 自己的握手、状态与加密格式，第三方互通需要适配这些约定。[产品说明](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/README.zh-CN.md)、[协议](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/SPEC.md)

值得保留的经验包括：进度收条与正式回复分开，避免互相回应“收到”；发送工具明确报告送达、排队与失败；CLI 与 MCP 共用会话引擎；验证发布程序的进程行为。其迭代记录说明，工具可调用、Agent 会选择正确工具、编译发布后可靠运行，需要分别验证。[迭代记录](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/CHANGELOG.md)

### 已确认的边界

| 方面 | 调研结果 | 对 CtrlX 设计的影响 |
| --- | --- | --- |
| 对话管理 | 每个 MCP 实例同时处理一场对话 | 需要单独管理任务及会话归属 |
| 邀请和唤醒 | 对方需在线运行 AgentHop；离线邀请不排队；Agent 主要通过等待工具获取消息 | 收到消息、唤醒 Agent 与用户批准是不同环节 |
| 联系人收件路由 | 同数据目录的两个 MCP 实例争用同一收件地址；本地实验中邀请仅出现在第一个实例 | Host 需要统一接收并路由邀请 |
| 失败清理 | 地址冲突导致首次建联失败后，清理 MCP 与 Relay 仍遗留两个本地监听服务 | 接入前需要修复首次启动失败的资源回收 |
| 身份核对 | 在已知完整配对码和目标公钥的前提下，实验中不持有目标私钥也能通过会话身份核对 | 联系人身份核对尚未在配对码之外形成独立的私钥持有证明 |
| 执行授权 | 用户同意的要求主要写在工具说明中，项目自身没有独立验证用户批准的机制 | 产品需要明确的任务授权和共享范围 |
| 恢复与产物 | 重连依赖原进程存活；单个附件最大 512 KiB | 持久化任务恢复和较大产物交换需另行设计 |
| 完成语义 | 消息送达和 A2A 消息 Ack 不代表共同任务已验收 | 任务完成需要实际产物与验证条件 |

路由与资源问题依据 [身份实现](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/identity.ts)、[收件实现](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/inbox.ts) 和 [Host 启动路径](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/host.ts#L68)。身份实验针对的是 [会话握手](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/session.ts#L159)，其前提包括完整配对码已知，不能解释成只知道联系人名字即可进入。加密邀请的发送者认证属于另一层机制。

其余边界见 [MCP 工具实现](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/mcp.ts) 与 [消息 Ack 实现](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/packages/cli/src/room.ts)。AgentHop 实现了消息与文件的端到端加密，同时明确没有前向保密；Relay 仍能观察连接与流量元数据。传输加密不替代端点、模型服务和任务授权的边界。[安全说明](https://github.com/sdyuyouth/agenthop/blob/0e3e733bc5703856b3924a27c0495c0736a58a92/SECURITY.md)

## 共用的产品基础

三个方向都可以围绕同一份任务记录组织：目标与验收条件、执行的 Host 和项目、参与的 Agent 实例、关联界面和文件、当前运行或产物版本、允许的动作和共享范围、当前等待谁、已经产生的结果与验证证据。

任务页需要将当前可观察的状态与 Agent 自述区分开。例如，Agent 报告“正在处理”属于进度；工具执行结果或测试记录属于证据；用户是否接受交付属于验收。流程、交付内容和依据之间应能相互追溯。

用户介入后，应把当前上下文交还给正确的 Agent。接管得到的操作记录可以在用户选择教学时生成工作流；跨用户会话的共同约定可以成为本地任务的约束。首个原型只实现验证所需的关联，数据模型随真实使用收敛。

不同 Agent 使用同一组项目资源，是面向多工具用户的待验证价值。新 Agent 的接入仍要符合资源授权与控制权交接；共用项目不表示同时操作同一页面或继承其他会话的授权。早期优先复用已有执行程序，避免为了呈现统一界面先重做通用 Agent 运行时。

## 建议的验证顺序

首轮可邀请 8–12 名已有真实项目、近期确实有离开电脑后继续工作需求的用户，进行约两周的探索性试用。该样本用于发现问题与重复使用动机，不足以推断总体市场规模或宣告产品市场匹配。

| 顺序 | 需要验证的问题 | 继续投入的依据 |
| --- | --- | --- |
| 1. 安装与首次成功 | 用户能否接入自己的一个项目，并从手机完成一轮实际修改和验收 | 记录安装、配对、授权、首次成功的耗时与放弃原因；区分独立完成与人工帮助 |
| 2. 真实任务对比 | 相比官方客户端、用户已有远程工具，是否少回电脑、少转述且结果不变差 | 同类任务比较到验收通过的时间、手工截图和解释次数、返回电脑次数、失败恢复与总成本 |
| 3. 自主重复使用 | 首次演示后，用户是否在有相同需求时主动再用 | 观察第二周真实机会中的使用比例、成功验收次数，以及明确费用下的付费选择 |
| 4. 演示复用 | 人工复现与检查步骤能否在下一次修改中复用 | 不同输入或新版本下仍有收益，维护成本低于继续手动处理 |
| 5. 跨用户协作 | 双方独立环境的协作是否减少转述和等待 | 先用已有协作关系做接口联调，确认再次使用后再扩大联系人和异步任务范围 |

对比应尽量保持模型、任务材料、网络与结果质量相近，分别记录首次配置成本和熟悉后的使用成本。产品功能开放情况不同，要记录套餐、版本和可用入口；无法启用某功能不能直接算成竞品没有该能力。

每次任务至少记录：开始与验收时间、是否回电脑、人工转述次数、接管及恢复结果、最终产物是否合格。另记录从通知到打开正确结果的耗时、选中文件或界面反馈是否准确，以及断线或 Host 不在线导致的中断。无远程需求的那一周不等于用户拒绝产品，需要与有机会却选择其他工具的情况分开。

如果结果质量持平时，官方客户端或现有工具已经同样省事，继续增加界面种类不会自动形成竞争力。若用户只观看演示、试用一次，之后有真实需求仍不再使用，应调整场景或目标人群。价格测试必须给出实际费用；口头表示喜欢不能替代再次使用和付费行为。

实时界面的流畅度、接管稳定性和反馈质量应先达到真实任务可用，再扩大界面和工作流数量。演示学习关注反复出现的人工操作；跨用户协作保留独立的小规模实验，不把双方同时安装和在线作为个人首次体验的要求。

上述顺序是建议，三个方向均未形成发布承诺。继续投入的依据应包括任务结果质量、用户实际节省的时间、重复使用和接入成本。只有演示效果、模型自报完成或一次通信成功，都不足以代替这些证据。

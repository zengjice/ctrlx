## 阶段 3-Fix 决定与落实（2026-11-14 确认，2026-11-16 实施）

- 触发问题：每次 Orbie 面板发送都会保存新的普通 Workflow 配置并启动 run，Orbiter 后续对话使用同一路径；Workflows 列表直接展示它们。已核对 `OrbieService.send`、`OrbiterService.deliver` 与 `AgentWorkflowService.handle`，以上为实施前问题；本轮替换此路径，证据见 STAGE3_FIX_TODO。
- Orbie、Orbiter 都是普通 Agent；Workflow 可由一个或多个 Orbiter 执行，Agent 不绑定单次任务生命周期。独立 Task、完成／归档状态和双任务上限由 3-Fix 移除。
- 共用的是 Agent 运行态、受保护输入、回执和原生回复核验；Workflow 保留图编排。普通交互的初始化和存储不能依赖 Workflow 加载成功。消息技术记录不升级为新的产品对象。
- 数据迁移依靠明确的关联 ID，保留原生会话、回复、材料、普通 Workflow 和未确认请求；先备份校验，再切换，禁止按名称清理或自动重发。
- 八项范围、A–E 实施顺序及验收矩阵已纳入 [STAGE3_FIX_TODO.md](STAGE3_FIX_TODO.md)。源码已按此边界实施，验证和剩余实机边界见执行清单；阶段 4–6 以新边界为前提，不沿用独立 Task 模型。

2026-11-16 补充 O-10：恢复能力在 Orbie／Orbiter 共用，复用已有恢复描述和原生 Resume；新标签使用新 AgentID，只有成功核验后才更新角色关联。旧对话、草稿、材料和历史请求证据保留，未确认请求不得导致恢复入口永久禁用。已补充关闭类型、历史缺失、CLI 失败、重复点击及恢复丢回包验收，当前已实现相关入口，具体证据与限制见执行清单。

以下阶段 1–3 收敛记录是历史事实；其中旧 Task、单步 Workflow、手动重连及当时身份表述不覆盖当前[身份契约](../../agent-identity.md)和 3-Fix 的修订方向。
